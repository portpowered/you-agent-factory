## Codebase Patterns
- Runtime worker taxonomy: author `INFERENCE_WORKER`, `AGENT_WORKER`, `SCRIPT_WORKER`, and `POLLER_WORKER` in `api/components/schemas/data-models/WorkerType.yaml` while keeping legacy `MODEL_WORKER` / `HOSTED_WORKER` accepted. Normalize enum values through `pkg/interfaces/public_factory_enums.go` and gate compatibility through `IsInferenceWorkerType`, `IsPollerWorkerType`, and `ProjectWorkerBehaviorClass` instead of comparing only legacy constants.
- Runtime workstation taxonomy: author `INFERENCE_RUN`, `AGENT_RUN`, `SCRIPT_RUN`, and `POLLER_RUN` in `api/components/schemas/data-models/WorkstationType.yaml` while keeping legacy `MODEL_INVOKE` / `MODEL_WORKSTATION` accepted. Normalize enum values through `pkg/interfaces/public_factory_enums.go` and gate compatibility through `IsInferenceRunWorkstationType`, `IsPollerRunWorkstationType`, and `ProjectWorkstationBehaviorClass` instead of comparing only legacy string constants. Map public `behavior: POLLER` through `internalFactoryWorkstationKindFromPublic` to `WorkstationKindPoller`.
- Worker/workstation behavior compatibility: compare normalized behavior labels via `RuntimeBehaviorClassLabel` (`INFERENCE_WORKER` pairs with `INFERENCE_RUN`) in `pkg/interfaces/worker_workstation_compatibility.go`; grandfather legacy `MODEL_WORKSTATION` + `MODEL_WORKER`, legacy `MODEL_WORKSTATION` + `SCRIPT_WORKER`, legacy empty standard workstations + inference workers, and poller script/hosted bindings through `IsLegacyGrandfatheredWorkerWorkstationPair`; enforce mismatches in `pkg/factory/validation/worker_workstation_behavior.go` (`WorkerWorkstationBehaviorCompatibilityTargets`) and expose them through POST `/factory-validations` plus `you factory validate <factory-path>`.
- Runtime taxonomy CLI/API inspection: keep authored worker/workstation strings intact in `apisurface.FactoryRuntimeTaxonomySummary`; human validate output flows through `apisurface.RenderFactoryValidationHuman` and loads factory paths via `factoryconfig.FlattenFactoryConfig` before `validationentry.ValidateFactoryAPI` with `ProfileTopology`.
- Keep `FakeService` and `RuntimeService` as parallel `factorysessionexecution.Service` implementations: mock-provider transports inject `FakeService` via `NewFakeService`, `NewFakeServiceFromContractFixtures`, `WithFakeScenarios`, and `WithPersistedSessionSeeds` without JavaScript runtime setup; real simple-workflow execution uses `NewRuntimeService` behind the same contract. Prove coexistence in `fake_service_coexistence_test.go` alongside `fake_service_test.go` and runtime-backed tests.
- Use `factorysessionexecution.PrepareStart` to normalize durable JavaScript session starts: it chains `NormalizeStartRequest`, `resolveStartSourceWithResolution`, wrapped-source validation (IIFE wrap matching `workflowruntime.Run`), args JSON checks, `workflowpolicy.Resolve`, and wait-option validation before runtime execution.
- Runtime simple-workflow fixtures live in `pkg/orchestrators/javascript/runtime/testdata/`; factorysessionexecution tests can read them via `../orchestrators/javascript/runtime/testdata/<name>`.
- Durable start source resolution is shared through `resolveStartSourceWithResolution`; `ResolveStartSource` is a thin wrapper returning only `ResolvedSource`.
- `RuntimeService` request-id replay stores the first observed async/sync start responses in `runtimeStartReplayRecord` (`asyncStart` / `syncStart`); sync timeout replays must return the stored `TIMED_OUT` shape even after the session eventually completes. Idempotency tuple hashing excludes `wait` options—use args/source/policy changes to prove conflicts in tests.
- `factorysessionexecution.RuntimeService` implements async/sync simple-JS starts via `PrepareStart` + background `workflowruntime.Run` (`runSession` closes per-session `runtimeDone` when execution finishes). `StartAsync` returns immediate `RUNNING`; `StartSync` waits for terminal completion or `wait.timeoutMillis`, returns `COMPLETED` with projected result JSON or `TIMED_OUT` with `SYNC_WAIT_TIMED_OUT` availability while keeping the session running unless `wait.cancelOnTimeout` is true. In-memory `GetSession`/`GetResult`/`ReadEvents` read `runtimeSessionState`; canonical events use `BuildCanonicalRuntimeSessionEvents` (`runtime-service` source). Use `busy-loop.workflow.js` for non-terminating sync-timeout tests; use `simple-final.workflow.js` for completion; use a temp-dir spin-loop workflow when proving eventual completion after sync timeout.
- Terminal runtime session results normalize through `projectRuntimeSuccessResult` (`workflowresult.ProjectPrimaryResult` + `workcontent.GeneratedPtrFromParts`); durable `PrimaryResult` is WorkContent JSON (e.g. `[{"type":"JSON","json":{...}}]`), not raw workflow return JSON. Prove API-shaped parity with `factorysession.SessionReadResponseToAPI` / `ResultResponseToAPI` plus `ValidateResultMatchesSessionRead` in `runtime_projection_test.go`.
- Canonical runtime session lifecycle events replay through `ReplaySessionProjection` (`session_event_projection.go`) into durable `SessionReadResult`/`ResultReadResult` projections; `BuildCanonicalRuntimeSessionEvents` may include bounded `resultSummary` text on `SESSION_RESULT_UPDATED`, and sync-timeout paths rebuild events after `SYNC_WAIT_TIMED_OUT` availability changes. Prove live-vs-replayed parity and idempotent replay in `runtime_event_replay_test.go`.
- CI `Build, Lint, and API` runs `make backend-size` on owned Go packages (100-line function cap). Split large test functions with `t.Helper()` assertion helpers (see `runtime_projection_test.go`) rather than inline assertion blocks.
