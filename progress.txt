## Codebase Patterns
- A reverse two-dot diff from a feature branch to current main can show every
  feature-added file as a deletion even when main never deleted it: those files
  simply do not exist at the merge base. Before treating that output as a
  reconciliation conflict, inspect the merge base and the actual merge result;
  a clean three-way merge retains the feature additions and applies only main's
  independent changes.
- ACP `_meta` is the protocol-sanctioned extension channel for namespaced
  custom data. When reconnect behavior requires an opaque, service-owned
  consumer identity that ACP core fields do not expose, advertise the
  extension in `AgentCapabilities._meta`, return the identity in the relevant
  session/prompt response metadata, and accept it only from the same
  namespaced request metadata key. A missing identity must mean a fresh
  consumer (or a safe rejection), never a guessed detached cursor; two
  consumers can share one ACP session ID while having different delivery
  positions.
- A stable cross-service collaborator that an operation uses on every call
  belongs on the owning service implementation as a constructor-injected
  narrow root capability. A transport callback may carry only per-operation
  values and callbacks; do not re-inject the collaborator per request. New
  stateful service operations also need payload-safe structured start and
  terminal-outcome logs from the injected logger.
- When a wire-level test passes a stub to a constructor that accepts a narrow
  service capability, embedding the broad service root does not make the stub
  automatically satisfy methods added later to that narrow interface. After
  reconciling with main, compile the wire package first and implement each
  newly required capability method explicitly on the test double; keep it a
  no-op when the constructor merely stores the dependency.
- `pkg/wire/wire_gen.go` is generated and can conflict whenever two branches
  change the provider graph. Restore a syntactically valid conflict side only
  as a temporary step, then run `go generate ./pkg/...` and
  `node scripts/check-wire-gen-drift.js`; commit the regenerated output, never
  a hand-merged generated file.
- Every client-visible update that is notified before its attachment cursor is
  advanced, including a synthetic retention-gap notice, must use the same
  conflict-safe acknowledgement helper. A version conflict after notification
  is stale optimistic state, not a reason to leave the delivered position
  retryable: refresh the version and retry before later retained catch-up, or
  the client can receive the update twice.
- A response-event bridge that runs alongside a synchronous invocation must
  stop its live `Next` reader and join it before calling the cursor's terminal
  `Drain`; sequence that retained tail with `context.WithoutCancel(ctx)` and
  return any resulting bridge error after an otherwise successful invocation.
  Cancelling the same context passed to `Sequence` can silently lose records
  exactly at the invocation-return boundary because the source cursor may
  still expose retained data while the Chat sequencer correctly rejects a
  cancelled operation.
- A resumable consumer cursor must be selected by a durable consumer identity
  when several detached candidates exist. Never select a candidate from map
  iteration: that makes reconnect order nondeterministic and can give one
  attachment another's acknowledged position. Preserve the legacy
  identity-less path only when there is exactly one candidate; otherwise
  return a typed ambiguity error without mutating any attachment.
- When event sequencing and stream-head advancement are separate optimistic
  operations, a live subscriber must wait until the session's StreamHead
  covers the observed record before notifying the client. This keeps the
  subsequent attachment acknowledgement possible and prevents a delivered
  record from being replayed by retained catch-up; test ready, lookup-error,
  and cancellation outcomes via explicit state/context signals, never a
  timer delay.
- Before trusting live CI status on a long-lived feature branch, check how
  many commits behind `origin/main` it is (`git log --oneline HEAD..origin/main`).
  A CI step can fail with a plain "file not found" / exit 127 if main has
  since merged a CI-infrastructure change (a new script plus a matching
  `.github/workflows/*.yml` step) that this branch's own checked-out tree
  doesn't have yet -- GitHub resolves the pull_request workflow definition
  fresh, but the job still checks out this branch's own commit, which is
  missing the file the new step invokes. Fix with a plain `git merge
  origin/main` (safe as long as `git diff --stat HEAD origin/main` shows no
  overlap with this PRD's own files), then re-diff
  backendsizecheck/pkgboundarycheck/pkgfilecountcheck against both a clean
  origin/main-only checkout and the pre-merge HEAD to confirm every
  difference is attributable to main's own pre-existing state, not this
  branch's diff, before pushing.
- The real `pkg/services/events/internal/service/subscribe.go` (Store.Subscribe)
  already delivers retained catch-up records (in commit order, preceded by
  one `DeliveryGap` if the starting cursor was evicted) BEFORE switching to
  live delivery, captured under the same lock as the live registration (see
  `Store.Subscribe`'s own doc comment and `catchupLocked`). A consumer that
  wants "retained-before-live, no missing/duplicate position across the
  handoff" does not need to sequence a separate Read-then-Subscribe call
  itself -- one `Subscribe` call from the stored cursor already satisfies
  that ordering guarantee end to end.
- To run something concurrently with an already-blocking synchronous
  transport call while a SEPARATE concurrent operation (e.g. a producer
  bridge) is already running alongside the same call via an established
  `RunWithXxx(ctx, ..., invoke)`-shaped owning-service function: add the new
  operation as an additional plain-function parameter to that SAME owning
  function (`RunWithResponseBridge` gained a second `liveDrain
  func(context.Context)` parameter alongside its existing bridge) and run it
  on a second goroutine joined the same way as the first, rather than
  inventing a second concurrency-owning wrapper. Keeps exactly one place
  (`pkgboundarycheck`-compliant, chat_sessions-owned) responsible for every
  goroutine/channel/cancel this feature needs, and the transport still only
  ever holds and calls plain function values.
- When a value is written inside a goroutine an owning-service `RunWithXxx`
  function spawns and fully joins before returning (channel close + receive
  establishes happens-before per the Go memory model), a caller may safely
  read that value immediately after the `RunWithXxx` call returns with NO
  additional mutex/atomic -- but only after that call returns, never before
  or concurrently with it. `dispatchFactoryInvocation`'s `liveDelivered`
  named return (written inside the `liveDrain` closure, read only after
  `s.responseBridge(...)` returns) relies on exactly this guarantee.
- A duplicate-suppression decision that only ever consults the LAST/most
  recent delivery attempt's own return value is a latent bug the moment a
  second, earlier delivery path is added alongside it (here: a live drain
  delivering a message, discarding its own success signal, while the
  post-invocation catch-up sweep's return value alone decided whether to
  fall back to non-canonical/final-only output) -- the earlier path's
  "did I deliver something" signal must be threaded through and OR'd in
  explicitly, not assumed to be implied by the later path re-observing it
  (it may not, if both paths correctly share one cursor and therefore never
  redeliver the same record). A test that seeds data only after the earlier
  path is confirmed listening, and asserts an exact notify call count (not
  just "at least one" or "no error"), is what catches this class of bug --
  a looser assertion would have passed even with the duplicate.
- A Python (or any non-Go) script that opens a Go source file in text mode
  and rewrites it on Windows can silently convert LF line endings to CRLF on
  write (Python's default text-mode newline translation uses `os.linesep`).
  `gofmt -l` then flags the whole file even though the Go syntax is
  unchanged, and `git status` shows a "CRLF will be replaced by LF" warning.
  Fix by reading/writing the file in binary mode (or just re-running the
  edit through the Edit tool instead of a shell script) -- `data.replace(b
  '\r\n', b'\n')` on the raw bytes restores it.
- `go run ./cmd/pkgboundarycheck -root .` forbids `pkg/transports/*` packages
  from containing ANY goroutine (`go` statement), `make(chan)`,
  `context.WithCancel`/`WithTimeout`, or `logging.EnsureLogger` call --
  literally: "prohibited transport concurrency/platform-selection behavior
  ... inject an exact service operation or external-effect edge; lifecycle
  belongs to Initializer and domain policy belongs to its service owner."
  This is the *automated, enforced* version of "don't hide service logic in
  the transport": if a transport needs to run something concurrently with a
  synchronous call it already makes (e.g. "start a producer bridge alongside
  a blocking Invoke call"), the transport must declare a plain function-typed
  collaborator (its own local type, e.g. `acp.ResponseBridge func(ctx, ...,
  invoke func(ctx) (T, error)) (T, error)`) and the OWNING SERVICE'S
  internal/wire package must own the goroutine/channel/cancel inside the
  concrete implementation it hands pkg/wire. The transport then only ever
  calls that one function value -- it never writes `go func(){...}()` itself.
  Verify with `go run ./cmd/pkgboundarycheck -root .` diffed against a clean
  worktree checkout of the pre-iteration HEAD (see the git-worktree-diff
  pattern below) *before* investing further in an implementation shaped the
  other way -- it fails fast and cheaply on this exact mistake.
- ACP outbound projection (record -> acpsdk.SessionUpdate) belongs at
  `pkg/transports/acp/internal/mapping`, per
  `docs/internal/projects/acp-client/final-proposal.md` §6.1/§8 -- distinct
  from `pkg/transports/mapping/` (generated OpenAPI contract mappers) and
  from the *inbound* provider-stream mapper at
  `pkg/services/providers/internal/services/execution/.../acp/internal/service/service.go`.
  Those two directions must not share code; final-proposal.md says to bind
  them only through a shared conformance fixture, not shared Go code.
- `workers.Draft` (pkg/services/workers/response_drafts.go) is the one
  normalized vocabulary owner for Kind/Phase/Payload/ItemID/ParentItemID.
  Transport mappers should consume it directly rather than inventing a
  parallel "record" struct -- keeps "no new event taxonomy" true.
- The legal (workers.Kind, workers.Phase) pairs are NOT the full 12x6 cross
  product. The one authority is `allowedPhasesByKind` in
  pkg/services/workers/internal/services/workstations/draftvalidation/validation.go.
  Notably: KindMessage and KindReasoning only ever carry
  {PhaseStarted, PhaseDelta, PhaseCompleted} -- PhaseUpdated never occurs for
  either, despite the PRD's own acceptance-criteria text mentioning
  "MESSAGE/UPDATED". Build against the validator's table, not literal PRD
  phase names.
- `pkg/services/workers/internal/services/workstations/draftvalidation/acp_l1_outcome_parity_test.go`
  is a test-only (no production symbols reachable outside `_test.go`) but
  authoritative declaration of the intended ACP L1 outcome
  (MESSAGE_CHUNK/THOUGHT_CHUNK/USAGE_UPDATE/GAP_NOTICE/ERROR_OUT_OF_BAND/NO_OUTPUT)
  for every legal (Kind,Phase) pair. Use it as the ground-truth table when
  building the full dispatcher (story 002) -- note it disagrees with
  prd.json's own text on KindError (parity test says ERROR_OUT_OF_BAND for
  every phase; prd.json's context/solution area implies no-output). Flag /
  resolve explicitly in story 002 rather than silently picking one.
- acpsdk.SessionUpdateAgentMessageChunk/AgentThoughtChunk carry only
  `MessageId *string` for item lineage (UNSTABLE, spec says UUID format).
  There is NO ACP wire field for ParentItemID, and no item-identity field at
  all on usage_update/session_info_update. "Preserve ItemID/ParentItemID
  wherever the ACP update contract supports lineage" (PRD 001-AC2) means:
  set MessageId from ItemID; ParentItemID has nowhere to go on the wire and
  should not be force-fit into Meta.
- Backend size limit is enforced per-function (100 lines) as well as
  per-file (1000 lines) via `go run ./cmd/backendsizecheck -root .` (must
  run from repo root -- `-root pkg` fails to find the exemption baseline
  file). Large Go table-driven tests MUST split into multiple smaller Test
  functions (one per category of case) with a shared `run*Cases` helper --
  a single big `tests := []struct{...}` + range-and-assert loop very easily
  blows the 100-line function cap. See existing convention in
  pkg/transports/acp/internal/protocol/*_test.go: many small, narrowly named
  Test functions, not one giant table.
- `golangci-lint run ./pkg/...`, `go run ./cmd/pkgfilecountcheck -root .`,
  `go run ./cmd/pkgboundarycheck -root .`, `go run ./cmd/pkgstructurecheck -root .`

- Any code that reads `chatsessions.Session.Version` to use later as an
  `ExpectedVersion` on a version-guarded call (`BindFactorySession`,
  `AcknowledgeAttachment`, `AdvanceStreamHead`, ...) must re-read it
  immediately before that call, not reuse a value captured earlier -- even
  one captured "just before" a call that looks synchronous from the
  transport's point of view. `dispatchFactoryInvocation` can run a Chat
  Sessions-owned concurrent bridge (`acp.ResponseBridge` /
  `factorysessionsshim.RunWithResponseBridge`) alongside the wrapped Factory
  invoke call, and that bridge independently bumps `Session.Version` via
  `AdvanceStreamHead` for every event it bridges -- so a version read at turn
  admission (`startResult.Session.Version`) is stale by the time
  `dispatchFactoryInvocation` returns whenever the turn actually streamed
  anything. This was a real bug (every real turn with response events failed
  `BindFactorySession`/`AcknowledgeAttachment` with `*chatsessions.ConflictError`)
  that shipped silently for two iterations because every prior test used
  fakes that never produced a real concurrent event during the call. `Server.
  currentSessionVersion` (session_prompt.go) re-reads via `GetSession`
  immediately after `dispatchFactoryInvocation` returns -- safe without a
  retry loop specifically because `RunWithResponseBridge` always fully joins
  its goroutine before returning, so nothing can mutate `Session.Version`
  between that read and the version-guarded call that follows it.
- When a prior iteration's notes claim "no production caller does X yet, so
  this code path always sees an empty/default state," re-verify that claim
  is STILL true before trusting it, especially after any later iteration
  wired a new producer into the graph -- don't just re-read the stale
  reasoning. The fastest way to check: actually run the one functional/
  integration test that exercises the real end-to-end path (not just the
  package-scoped unit tests the note's own "Verified" section lists) --
  `go test ./tests/functional/... -run <Name> -v -count=1` -- and read the
  failure, not just re-derive from prose. This session found a real,
  previously-shipped-broken functional test this way in under a minute,
  where continuing to trust the stale note would have left it broken.
- To find the underlying cause of an opaque `*acpsdk.RequestError{code:
  -32603, data:{"reason":"dependency_unavailable"}}` (this transport's one
  bounded classification for every non-cancellation dependency failure --
  see `classifyDependencyFailure`), temporarily add a `println("DEBUG",
  cause.Error())` (or `t.Logf` of the harness's own captured `stderr`
  buffer, if the log line would go there) right before the classification
  call, rerun the one failing test, read the real underlying error, then
  revert the debug line before committing. The classification is
  intentionally payload-free for clients; do not leave temporary debug
  prints in committed code.
- Legalizing a new `workers.Phase` for an existing `workers.Kind` in
  `draftvalidation.allowedPhasesByKind` can retroactively un-suppress
  unrelated, pre-existing (Kind,Phase) pairs that a completely different
  service already produced and that draftvalidation's own rejection
  previously scrubbed from every observable event stream by accident, not by
  design. Concretely: legalizing `KindSession/PhaseUpdated` for
  session_info_update also un-suppressed a pre-existing quirk in
  `pkg/services/providers/internal/services/acp/internal/service`'s ACP-wire
  progress synthesis (a `SessionInfoUpdate` notification gets modeled as a
  `kind="session"` "started" marker, and `progress.go`'s own
  `completedPromptProgress` then synthesizes a matching "completed" closing
  marker for it) that always produced two `KindSession/PhaseUpdated`
  response events with no real content
  (`SessionPayload{Status:"updated"}`, `Title` always nil since that mapper
  was never updated to populate it) -- previously silently rejected as an
  illegal pair, now valid and visible, which broke an unrelated pinned
  golden test (`tests/functional/providers/acp`'s
  `TestYouRunUsesPinnedACPWireGoldensAndProjectsTerminalOutput`) two
  iterations after the phase was legalized, not in the same iteration that
  legalized it. Before legalizing any new (Kind,Phase) pair, grep the whole
  repo for every existing (not just this PRD's own) producer of that Kind to
  check for this kind of accidental-suppression byproduct, and re-run
  `go test ./... -short` (not just this package's own tests) afterward.
- `go test ./... -short` in this repo currently has several unrelated,
  pre-existing governance/inventory-check failures with no connection to
  this PRD: `internal/ownershipinventory`, `internal/migrationledgercheck`
  (and its `cmd/` counterpart), `cmd/packagetargetmanifestcheck`,
  `internal/exemptionbudget`, `internal/functionaltestmetadata`,
  `internal/providercatalog`, `internal/testutil/responsestreamremovalgate`.
  These reference package structure (`pkg/services/chat_sessions/wire`,
  `pkg/services/events`) created by already-merged, unrelated earlier PRDs,
  and a `docs/temp/functional-tests-expansion/migration-ledger-inventory.json`
  that was never part of this branch's committed tree at all (confirmed via
  `git log -- <path>`) -- not something any iteration of this PRD deleted.
  Do not chase these; confirm any newly-observed `go test ./... -short`
  failure is actually caused by this PRD's own diff (compare against a
  `git worktree add --detach` checkout of the pre-iteration HEAD) before
  investing time in it.
- `chatsessions.Service.AcknowledgeAttachment` cannot be used to "skip" an
  attachment's cursor across a retention gap, even deliberately: it always
  re-validates by calling `events.Service.Read` from the attachment's own
  *currently stored* `AfterSequence` toward the requested position (see
  `pkg/services/chat_sessions/internal/service/sequencing.go`'s
  `AcknowledgeAttachment` + `verifyAcknowledgeAttachmentReadReachedRequestedPosition`),
  and rejects with `*chatsessions.AttachmentRetentionGapError` the moment
  that internal read can't prove the full span was retained -- regardless of
  what position you ask to advance to. There is no "acknowledge past the
  gap" escape hatch in L1 V2. This means the *only* way this transport can
  legitimately surface a `STREAM_GAP` is a real producer-committed
  `workers.KindStreamGap`/`PhaseUpdated` record already sitting in the
  aggregate stream in its correct commit-order position (the existing
  `drainRecords`/`mapping.Project` path already handles this with zero new
  code -- `KindStreamGap` was already a legal, dispatched pair from story
  002). A *transport-observed* `events.ReadOutcomeGap` (this connection's own
  stored cursor already stale before any such record could ever be read) has
  no such producer-committed record to replay, cannot be bridged into an
  in-band notice through AcknowledgeAttachment, and is correctly left as the
  existing bounded `errStreamGapEncountered` hard failure -- do not try to
  "fix" that path into a synthetic gap notice without a design change
  upstream in chat_sessions.
- `identity.NewConnectionID()` mints a fresh connection identity on every
  `Serve()` call and `chatsessions.AttachRequest` has no resume-position
  input, so under the current V2 T03 transport there is no protocol-level
  way for a *new* stdio connection to resume a *specific* prior attachment's
  cursor -- that requires `session/load`/`session/resume`, both already
  negotiated but still dispatched as method-not-found (see
  `pkg/transports/acp/internal/protocol/protocol.go`), which is future-story
  scope, not T03's. "Disconnect and reconnect" for story 004 is therefore:
  disconnect = release the old attachment via `chatsessions.Service.Detach`
  (new `Server.detachAttachments`, deferred once per connection in
  `serveConnection`, using `context.WithoutCancel(ctx)` so it still runs
  after the context that ended the connection is itself already canceled);
  reconnect = a fresh connection's fresh `Attach` replaying currently
  retained history once from position 0, proven not to be corrupted by the
  prior connection's detach.
