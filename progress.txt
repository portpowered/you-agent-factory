## Codebase Patterns
- `buildRuntimeBundle` in `pkg/service/factory_build.go` returns `factoryRuntimeBundle`, the single runtime wiring struct referenced from `liveRuntimeHandle`; add new runtime sidecars on `factoryRuntimeBundle` only—startup (`BuildFactoryService`) and `buildReplacementFactoryRuntime` both create `logSink` and session loggers inside `buildRuntimeBundle`, not after the fact.
- Register every live session (including `~default` at `Run` startup and `OpenFactorySession` launches) through `registerLiveSession` in `pkg/service/runtime_sessions.go` with explicit `FactorySessionTarget` metadata; use `defaultSessionTargetFromRuntimeBundle` for default startup—do not call `sessions.Upsert` directly except in `replaceSessionRuntime` replacement updates.
- Route session-scoped work, snapshots, idle guards, and record/replay paths through `SubmitWorkRequestForSession`, `GetEngineStateSnapshotForSession`, and `requireIdleRuntimeForSession` in `pkg/service/runtime_sessions.go`; use `sessionScopedRecordPath` for per-session replay artifacts—do not read `fs.currentFactory()` when `session_id` is explicit.
- Canonical validation-target test assertions for API-shaped targets live in `pkg/testutil/validationassert` (`HasTarget`, `HasTargetCode` on `[]factoryapi.FactoryValidationTarget`); `HasTargetCode` accepts an optional topology failure label to preserve service-test diagnostics—import only from `_test.go` files. API tests in `pkg/api/server_factory_test.go` and `pkg/api/servertests/server_factory_validation_test.go` use `validationassert` directly (no local `assertHasValidationTarget*` in `pkg/api`).
- Batch upsert success responses expose per-work identifiers via `UpsertWorkRequestResponse.works` (`name`, `workTypeName`, `workId`); build domain metadata with `requests.WorkRequestSubmitResultFromNormalized` in the engine and mock factory (primary-work fields plus `Works` slice), then map through `upsertWorkRequestResponse` in `pkg/api/handlers.go` for default and session-scoped PUT routes.
- Load filesystem-path `FACTORY_REQUEST_BATCH` JSON for CLI ingress through `pkg/cli/batchload.LoadFromFile`, which wraps `pkg/factory/requests.ParseCanonicalWorkRequestJSON`; keep `run.LoadWorkFile` as a thin delegate for existing callers and future `you submit batch` file modes.
- Register `you submit batch` under `newSubmitCommand` via `pkg/cli/root_submit_batch.go`; unary flags stay on parent `submit` only; batch help documents ingress modes and `you docs batch-inputs`; wire `RunE` through injectable `submitBatch` → `submitcli.SubmitBatch`. File-path HTTP/dry-run lives in `pkg/cli/submit/batch.go` with `resolveBatchInput` in `batch_input.go` (inject `BatchConfig.Stdin` / `BatchConfig.StdinIsTTY` in tests; piped no-arg stdin and explicit `-` use `batchSource=stdin`; file path ignores stdin); inline JSON positionals use `looksLikeInlineJSON` (first non-whitespace `{`) with `batchSource=inline` and no `os.Stat`; `--file <path>` and `--file -` win over positional paths via `resolveBatchFileFlag`. Human `201` stdout belongs in `printBatchSuccessHuman` (`pkg/cli/submit/batch_output.go`): request/trace/work-count lines, optional `relationCount` from parsed request relations, up to ten per-work lines with `you work show` / `you work list --name` hints, truncation summary for longer lists—never print payloads; `--verbose` logs endpoint, batchSource (file, stdin, inline), byte size, requestId, and work count on stderr—never payload content. Structured `--json` success and dry-run payloads belong in `BatchSubmitJSONResult` via `printBatchSuccessJSON` / `printBatchDryRunJSON` in `batch_output.go`: include `requestId`, `traceId`, `workCount`, `relationCount`, `sessionId`, `endpointPath`, `batchSource`, and per-work `works` on HTTP success; dry-run adds `dryRun: true`, `workNames`, and omits `traceId` unless present in parsed input.
- Human-mode `you submit` success stdout is formatted in `pkg/cli/submit/human_output.go` via `writeHumanSubmitSuccess`: lines for `Submitted: <name> (<workTypeName>)`, `traceId`, optional `workId`, then `Verify: you work show <work-id>` or fallback `workId was not returned; verify with:` + `you work list --name <name>`; use `submitResponseString` for API pointer fields with request fallbacks; httptest proof in `TestSubmit_HumanStdoutIncludesWorkMetadataAndShowHint` and `TestSubmit_HumanStdoutFallsBackToWorkListWithoutWorkId`.
- `--json` submit success uses `pkg/cli/submit/json_output.go` (`SubmitSuccessResult` / `writeJSONSubmitSuccess`): emit `workId` (pointer, omitted when absent), `name`, `workTypeName`, `traceId`, `sessionId` (API field, else `clidiag.SessionLabel`, else `sessionpath.DefaultFactorySessionID`), and `endpointPath` from `sessionpath.ScopedPath`; proof in `TestSubmit_JSONStdoutEmitsStableSuccessEnvelope` and `TestSubmit_JSONStdoutEmitsSessionScopedEndpointPath`.
- Submit failure surfaces live in `pkg/cli/submit/error_output.go` (`submitFailureError`): transport errors as `factory not reachable at <url>` with empty stdout; non-201 responses as `submission failed (<status>): <message>` from `ErrorResponse.message` or a bounded raw-body preview (`submitErrorBodyPreviewLimit` = 200 runes/bytes); optional `workId=<id>` suffix from best-effort JSON parse; proof in `TestSubmit_FactoryNotRunning`, `TestSubmit_ServerError`, `TestSubmit_NonJSONErrorBodyUsesBoundedPreview`, `TestSubmit_ErrorIncludesWorkIdWhenPresent`, and `TestSubmit_JSONModeDoesNotEmitSuccessOnFailure`.
- Extend `SubmitWorkResponse` in `api/components/schemas/api/SubmitWorkResponse.yaml`, regenerate via `make generate-api` (Go + UI), populate `interfaces.WorkRequestSubmitResult` from `requests.WorkRequestSubmitResultFromNormalized` after normalization in engine/mock factory, and map through `submitWorkResponseFromResult` in `pkg/api/submit_work_items.go` (not a separate `submit_response.go`—`pkg/api` has a 15-file cap) in both `SubmitWork` (`factorysessions.DefaultSessionID`) and `SubmitWorkBySessionId` (path param); assert `workId`, `name`, `workTypeName`, `traceId`, `requestId`, `accepted`, and `sessionId` in `server_submit_work_test.go` and session scoping tests.
- Session-scoped PNG import activation uses `activateImportedFactoryForSession` in `ui/src/api/named-factory/api.ts`: GET current factory via `getCurrentFactoryDocument`, preserve session `name` on the imported payload, PUT via `saveCurrentFactoryDocument` with incremented `version`, and map `CurrentFactoryDefinitionError` (including `STALE_FACTORY_VERSION`) into `NamedFactoryAPIError`; never `POST /factories`.
- Non-default session import isolation proof lives in `tests/functional/runtime_api/factory_transformation/api_current_factory_put_test.go` (`TestCurrentFactoryPUT_NonDefaultSessionImportIsolatesDefaultFactoryAndMaterializesBundledFiles`): `openNamedFactorySession` + `saveCurrentFactoryForSession` with imported-style bundled payload, assert session GET readback, unchanged default session/`alpha` on-disk config, and bundled files materialized only under `rootDir/<session-factory-name>/`.
- Dashboard import threads `useDashboardSessionStore.selectedSessionID` through `DashboardBento` → `useCurrentActivityImportController` → `useFactoryImportActivation({ sessionID })`, which defaults to `activateImportedFactoryForSession` so tab switches before confirm retarget activation without reload (mirror `useCurrentFactoryExport` session routing).
- `App.import.test.tsx` mocks `/factory-sessions/{session_id}/factory` by HTTP method (GET with `version`, then versioned PUT) and asserts no `POST /factories`; use `createDeferredPromise` from `app-shell-export-test-utils` to observe `Activating factory...` submitting state before resolving PUT.
- Inline single-use workflow-activity layout class strings directly on JSX in `workflow-activity-bento-card.tsx`; assert the graph panel shell via the viewport region’s `section[aria-labelledby]` parent in `workflow-activity-bento-card.test.tsx` (contains `relative`, `h-full`, `min-h-0`, `min-w-0`).
- Batch submit validation and HTTP failures stay distinguishable: canonical parse/validation errors fail locally before HTTP; non-`201` responses use `batchSubmissionHTTPError` in `pkg/cli/submit/batch.go` (`ErrorResponse.message` when present, otherwise a 200-byte bounded body preview); `--json` leaves stdout empty on validation or HTTP failure.
- End-to-end `you submit batch` against a live factory belongs in `tests/functional/smoke/cli_submit_batch_smoke_test.go` with checked-in `tests/functional/smoke/testdata/cli_submit_batch_smoke.json`; reuse `buildYouCLIBinary`, `reserveLocalTCPPort`, and `writeDefaultMockWorkersConfig` from `cli_factory_prompt_run_smoke_test.go`, start `you run --continuously` with mock workers, poll GET `/work` for readiness, then assert human success markers (`requestId`, `traceId`, `work count`, per-work line, `you work show` hint) plus API acceptance of the upserted work name.
- Parse worker/workstation `openCodeAgent` through `pkg/config/agents_config.go` with `validateOpenCodeAgentInFrontmatter` (rejects explicit empty or whitespace-only values), merge via `applyWorkerRuntimeExecution` / `applyWorkstationRuntimeIdentity`, and resolve dispatch precedence with `interfaces.ResolveOpenCodeAgent(workstation, worker)`.

- Header-only structured submit-work (`name`, `workTypeName`, `items: []`) is accepted in `pkg/api/submit_work_items.go` via empty-array early returns in `validateSubmitWorkItemsField` and `submitWorkItemsToContent`; API proof lives in `TestSubmitWork_AcceptsHeaderOnlyStructuredSubmitWork` and `TestGeneratedAPIIntegrationSmoke_SubmitWorkItemsAcceptHeaderOnlyStructuredSubmission`.
