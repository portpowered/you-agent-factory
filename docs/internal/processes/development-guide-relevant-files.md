# Development Guide Relevant Files

This inventory records the checked-in files and directories that the maintainer development guide should describe when it gives repository-root workflow instructions.

| Path | Role | Notes |
| --- | --- | --- |
| `go.mod` | Repository-root marker | Maintainer commands and worktree-aware tests should treat the directory containing `go.mod` as the canonical repository root. |
| `.github/workflows/ci.yml` | Required PR lane contract | Repo-owned PR checks should keep `actions/setup-go` pinned to the same patch-level Go toolchain declared by `go.mod` when cache restore is enabled; otherwise setup-go can download the newer toolchain into `GOMODCACHE` before cache extraction and fail with tar `File exists` collisions before the backend verification lane even reaches `make test-backend-verification`. |
| `Makefile` | Root command surface | The development guide should describe quality and generation commands as root-level invocations instead of teaching a nested package workflow; maintainers also rely on this file to preserve repo-owned `typecheck`, `release`, functional-lane, API generation or verification commands, the canonical verification tiers `make verify-fast`, `make verify-pr`, and `make verify-extended`, the direct `make backend-size` and `make pkg-maint` maintainer gates, their inclusion inside `make lint`, the split `make long-tests-managed-runtime` and `make long-tests-functional-runtime` subtargets that keep long local inference debuggable without duplicating raw `go test` invocations in workflow YAML, and the enforced backend coverage threshold through `GO_COVERAGE_MIN`. Contributor-facing aggregate tiers should print a human-readable owned-suite or lane label before each nested `make` step and emit the exact rerun target when that step fails, so contributors can recover from a failure without reverse-engineering nested `make` output. Keep the pull-request-equivalent tier duplication-free by routing each required lane through one owned target exactly once instead of mixing canonical targets with compatibility aliases for the same confidence outcome. Keep `make lint` subcommands centralized through `LINT_TARGETS` so command-owner tests can execute the same aggregate path with a focused target list instead of source-scanning Make output or running unrelated UI/deadcode side effects. Apply that same labeled-rerun pattern to opt-in long or specialty aggregates such as `make verify-extended` and `make long-tests`, and keep maintainer docs explicit about which deeper runtime risk each long subtarget covers. When long local-inference coverage is split or consolidated, keep compatibility aliases such as `long-tests-managed-runtime`, `long-tests-functional-runtime`, and `long-tests` on the root command surface until every repo-owned workflow and rerun path has moved to the same target names. Apply the same compatibility rule when CI lane names or `make` entrypoints are renamed on `main`: preserve transitional aliases such as `verify`, `test-ui-coverage`, `test-ui-browser-integration`, and `test-backend-verification` until reviewed PR heads and rerun workflows all speak the same command surface. In the maintainer guide, keep one explicit matrix that maps each canonical tier or lane to its owned subcommands, intentional exclusions, exact rerun path, and any remaining compatibility alias so future test-surface changes do not scatter ownership rules across multiple paragraphs. |

## Reusable Rules

- When maintainer docs describe command execution, anchor the instructions to the repository root that contains `go.mod` and `Makefile`.
- When a customer-facing reference topic grows into a stable packaged `you docs <topic>` surface, update both `docs/reference/*.md` and `pkg/cli/docs/reference/*.md` together, then keep `pkg/cli/docs/docs.go` plus `pkg/cli/docs/docs_test.go` aligned so the packaged topic list and embedded markdown stay in sync.
- Keep cross-platform maintainer command logic in repo-owned Go entrypoints such as `cmd/functionallane/` or `cmd/releaseprep/` instead of embedding platform-specific shell discovery pipelines directly in `Makefile`.
- If a workflow temporarily changes directories, state that it starts from the repository root and why the subdirectory hop is required.
- When GitHub Actions or other automation is added, prefer repository-owned root commands or package scripts that the maintainer guide already documents instead of inventing CI-only command sequences.
- For pull-request GitHub Actions jobs that need the reviewed branch contents, prefer checking out `${{ github.event.pull_request.head.sha || github.sha }}` instead of the default ephemeral PR merge ref so reruns do not fail fetches partway through a workflow after earlier jobs, later matrix legs, or platform-specific lanes have already started.
