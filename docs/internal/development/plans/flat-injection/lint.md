# Flat injection: static enforcement design

This appendix implements the enforcement policy of [the governing plan](plan.md), especially its architecture, rollout, verification, and [task packets](tasks.md). T20 owns checker infrastructure and construction placement; T23 owns strict injected-dependency policy and migrated constructor callers; T24 owns platform helper and compatibility retirement. T29 owns final enforcement, T22 owns integrated performance/release evidence, and VAL01 owns independent read-only loopback. The task IDs are the handoff references; this document does not authorize implementation. Source evidence was inspected on 2026-10-02; line numbers identify the audited checkout and may move.

## 1. Outcome and policy

Customers must observe the same execution, cancellation, replay, and diagnostics regardless of which internal owner invokes a capability. A valid process must have one canonical origin for each shared effect and fully constructed collaborators before activation. Static evidence must detect regression without confusing dependency topology with customer behavior.

Internal constructors assume their required injected dependencies are valid. They assign those dependencies directly and do not check nil, synthesize replacements, call fallback getters, install silent substitutes, or construct another service graph. Their operations also assume the injected dependencies exist. Error handling for an actual operation remains required.

The public process construction boundary may normalize supported optional host inputs once, select explicit disabled/no-op implementations where product configuration permits them, and reject invalid host input. After normalization, every internal required capability is present. Quiet logging selects its intentional implementation at this boundary; individual service owners cannot infer quiet mode from a nil logger. Optional domain data remains optional.

These are planning rules, not claims that the audited implementation already conforms. T23 must update internal constructor tests that currently expect missing-dependency errors while preserving documented public boundary errors. Changes to existing exported construction APIs require Current/Proposed excerpts in the owning task before their callers migrate.

## 4. Detection rules and limits

The constructor inventory names qualified service constructors, effects, their required parameters, returned service interfaces, and approved focused provider operations. It is enforcement metadata with exact semantic meaning, not a broad exception list. Validate references against source and reject stale entries. Derive provider references from authored Wire sets where possible and resolve exported aliases in owner Wire packages. Go internal visibility still applies: canonical composition consumes focused owner exports rather than importing private implementation packages.

Required rules:

1. A strict injected constructor or method cannot compare a classified required dependency with nil, branch on its existence/type to suppress behavior, return a substitute, or assign a default. A nil receiver compatibility check is rejected only where that receiver is a classified constructed owner, rather than arbitrary domain values.
2. Registered behavioral constructors cannot run from request/activation/opening operations, nested constructor bodies, deferred factories, or post-construction bind helpers outside approved focused providers. Normal state, scope identity, cancellation, file/network/process resource handles may still be allocated by their lifecycle owner.
3. Operational code cannot acquire registered shared real effects or no-op effects. Explicit root selection, policy-free leaf adapter implementations, and views over injected origins are allowed through exact operation rules.
4. Required dependency storage cannot use dependency bags, getters selecting implementations, or package-global mutable constructor registries once its capability set is migrated. Cohesive domain request/configuration records remain allowed.
5. Required dependencies cannot be hidden through local aliases, helper fallback wrappers, closures, or failed type assertions. Track parameter-to-field assignment and local aliases; summarize identified same-package helpers. Emit an actionable unresolved-classification finding when evidence is insufficient rather than silently claiming enforcement.

The first implementation should reuse AST/import infrastructure with a bounded alias/provenance index. If imported type aliases, shadowing, or generic wrappers cannot be resolved reliably, add a focused type-aware loader and define build tags/target platform coverage explicitly. Do not broaden a `New` name heuristic to simulate semantic resolution. Arbitrary interprocedural equivalence is outside a purely syntactic rule's proof; report that limit.

## 5. Semantic exclusions and fixture matrix

Classify dependencies by qualified contract and construction provenance, not names, all pointers, or all interfaces. Normal error branches, request validation, context normalization, optional domain payloads/schema fields/configuration, empty maps/slices, scope state, resources not yet opened, and actual unsupported operation handling remain valid. Explicitly configured disabled behavior receives an injected implementation; absence of a required logger/clock/runner is not a feature setting.

| Fixture family | Required examples and expected result |
| --- | --- |
| Dependency guards | Constructor nil error, fallback assignment, returned fallback getter, nil-gated publish/log/execute, boolean/interface assertion fallback: reject for registered required dependencies. |
| Provenance | Field assignment, local alias, local helper, deferred closure, imported constructor alias, parameter renamed: preserve detection. |
| Name resolution | Aliased import, dot import, package identifier shadowed by local variable, generic/local functions named `New`: distinguish exact registered symbol from unrelated function. |
| Logger/time | Service `EnsureLogger`, no-op literal, `zap.NewNop`, real-clock acquisition: reject; canonical explicit quiet mode, injected adapter, `.With`, `.Named`, timer from injected clock: allow. |
| Domain values | Optional payload/config field, nil error, request validation, lifecycle handle before opening, nil context normalization: allow. |
| Construction kind | Registered child service inside operation: reject; state maps, buffers, `NewReader`, `context.WithCancel`, scope identity, resource opening by owner: allow. |
| Boundary validation | Supported public `root.BuildProcess` input normalization: allow; repeated internal normalization: reject. Preserve exact public bad-input response evidence. |
| Source/build handling | Generated files and fixture files excluded consistently; `_test.go` fake/no-op selections allowed at test outer boundary; compiled support helpers cannot bypass production policy. Test applicable build-tag/platform variants. |
| Allowances/rollout | Exact valid provider allowance passes; stale symbol, widened operation, new violation in enabled capability, baseline suppression attempt: fails. |

Scanner fixtures are unit tests of the checker. Repository scans are static evidence. Functional tests must not assert constructor counts, pointer identity, dependency inventories, or source layout; they prove injected time, emitted diagnostics, isolation, and public lifecycle outcomes through supported boundaries.

## 6. Staged enforcement and parallel ownership

T20 can implement report/qualified-construction infrastructure in parallel with service migrations. T23 owns boundary dependency classification and the guard/fallback rule definitions (per-owner fallback removal belongs to the lane that rewrites that function, see inventory.md); the owners coordinate `pkgboundarycheck` aggregate/report files, with one integration owner applying those shared edits. Each service lane removes its own violations and supplies exact provider/required-capability metadata. T24 retires the shared fallback helpers and compatibility paths; T29 enables final repository scope, T22 produces integrated performance/release evidence, and VAL01 independently verifies integration.

1. Report observed violations and unresolved classifications with stable qualified symbols; do not introduce a giant baseline.
2. Enable strict rules for complete named capability sets, first shared clocks/logging and then migrated service construction families. A set has zero findings and a named owner before enablement. Remaining sets have task IDs and completion gates, not directory-wide exemptions.
3. Apply exact temporary compatibility allowances only where a migration step must remain releasable, with owner, reason, and deletion task. Reject additions and stale allowances. Existing unrelated baselines remain deletion-only.
4. T29 (split from T20 by the validation review because it depends on every owner lane) removes staged scope restrictions and all migration allowances after T24 helper retirement, runs full static gates, and records unresolved analysis limits explicitly. A production silent fallback or internal dependency nil guard is a stop condition for that enabled capability set.

Rollback reverts the affected independently valid slice and its enforcement metadata together. It must not reinstate a blanket exemption or silently accept a new fallback. No persisted-format migration or public behavior feature flag is required for checker rollout. Logging diagnostics expose symbol/path metadata only and must not dump environment or customer input.

## 7. Verification and integration

`LINT_TARGETS` includes `pkg-maint`, `pkg-boundary`, `service-cycle-check`, `golangci-lint-run`, and `repolint`. Durable construction runs in `cmd/repolint` through `go vet -vettool`, replacing the durable scanner and its target. Logging uses the pinned golangci-lint configuration. Registered T20 construction still runs through `pkg-boundary` pending its analyzer cutover. Backend Lint requires canonical lint on every PR and main push; do not add a competing checker execution path.

T20 metadata now belongs to `internal/lint/analyzers/construction_registry.go`. `RegisteredConstruction` resolves qualified calls and constructor references with `pass.TypesInfo`, returns observations as `[]ConstructionFinding`, and sends enforced findings through the shared exact baseline. Fixtures configure an invocation-owned registry; the repository's chat-target-catalog remains report-only. The temporary `contractguard` aliases keep the retained scanner consuming this same metadata. Guard/storage/getter summaries and focused-provider recursion/dispatch remain scanner-owned until their typed replacements land; then delete the scanner and aliases together. This seam does not enable any additional owner or establish full T20/T29 coverage.

Required evidence, per change and per PR, free or bounded local resource use:

- Unit/controlled: `go test ./internal/lint/analyzers ./cmd/pkgboundarycheck ./cmd/pkgmaintcheck ./cmd/servicecyclecheck`; fixture matrix proves specified matches and exclusions, not application behavior.
- Static/per PR: `make golangci pkg-boundary service-cycle-check pkg-maint`; enabled sets have zero violations and stale allowances. `repolint` compiles the canonical tag union; excluded imports are read with `ImportsOnly`, while excluded call bodies require native platform/tag coverage.
- Static/integrated gate: `make lint`; canonical complete target inventory passes on integrated head.
- Functional/controlled: governing plan's time, diagnostics, concurrency, cancellation, and replay witnesses prove real injected dependency behavior. Use shared `root.BuildProcess`, explicit scenario Factory Sessions, exact controlled edges, scenario isolation, and canonical bounded runner.
- Integrated evidence/T22 and independent loopback/VAL01: inspect actual generated Wire origins and run clean environment public journeys; distinguish source enforcement proof from untested runtime edges.

No paid provider calls are needed to prove these rules. Constructor-requiredness failures at the public host boundary, operational errors, and existing config validation remain characterized separately from internal topology. Implementation stops at pushed head/open PR/CI started/blocking feedback addressed; review owns terminal CI, conflicts, and merge as specified in the governing plan. Because per-site ratchets and exact baselines can pass on two PRs separately and fail on main, review rebases onto current origin/main and re-runs `make lint pkg-file-count` (plus `make generate-wire` and a diff check when Wire changed) on the rebased head immediately before every merge; a stale-green merge is forbidden (operator decision, 2026-10-02). Requiring up-to-date branches in GitHub settings is a repository decision outside this plan.
